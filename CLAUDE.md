# PrepPulse

Entry for the Presage SmartSpectra SDK Challenge on DEV (deadline 22 Nov 2026, 11:59 PM PST).

A desktop app (Electron + Node.js) for students preparing for high-stakes exams (JEE/NEET, SAT, A-levels). A student takes a timed mock test while the webcam measures pulse and breathing with the SmartSpectra SDK. Afterwards they see "Your pressure map" (how their body responded, question by question), plus a short breathing reset drill. Everything is compared with the student's own baseline, never with "normal ranges".

## Hard rules (contest + ethics), apply to all work

- No diagnosis, treatment, or medical claims. Never use words like "anxiety detection", "diagnose", "at-risk", "disorder", "healthy/unhealthy". Use phrasing like "your body's response" and "compared with your own baseline". (Presage's own docs: SDK metrics are for general wellness and informational use only, not FDA-cleared.)
- Camera only turns on after explicit opt-in consent. No covert monitoring. The SDK camera is opened only from the `vitals:start` IPC handler, which the renderer calls only after the student pressed "I agree, start camera" in this app run. Consent is not persisted; it is asked again on every launch.
- Process on the device. Never save or upload video frames or face images. Do not subscribe to the SDK `videoOutput` event unless a frame stays in memory for display only.
- SDK telemetry disabled (`enableTelemetry: false`) unless the developer decides otherwise. Keep the network facts below current.
- Any stored data is local only, with a clear delete option. No accounts.
- The API key is read from `.env` (`SMARTSPECTRA_API_KEY`, gitignored). Never print it, log it, send it to the renderer, or hardcode it. `.env.example` holds a placeholder.
- Writing style: no em dashes anywhere.
- Report wording: the post-test report is "Your pressure map", subtitle "How your body responded, question by question". Never use the words stress, anxiety, panic, nervous, or any judgement of the student (good/bad, better/worse, normal). Observations describe only what was measured: never why it happened, never whether it is good or bad, never a comparison with other people. `test/report.test.js` scans generated text and the window's source for these words.
- Measurement pauses are data, not noise. Measurement can pause whenever the student moves out of position (any non-OK validation status, `kStarting`, an SDK error, or no new stable sample). Every feature must record each pause as a gap with its start, end and reason (the validation code), show it honestly (for example "not measured: moved out of view"), and never interpolate, smooth or carry a value across it. Medians and charts use measured samples only.
- Support content is triggered ONLY by what the student says. The support screen ("Need to talk to someone?", Tele-MANAS and findahelpline.com) appears after the test only when the student answers "Really overwhelming" to the optional check-in, or when they open it themselves from home or Settings. Never trigger it, or anything like it (a message, a suggestion, a link), from pulse, breathing, HRV or any other measured signal. `needsSupportScreen()` in `lib/checkin.js` takes the answer and nothing else; `test/checkin.test.js` ("signals never trigger support") checks the function and the code paths that call it.

- Process safety (dev work on this machine): only stop processes you started yourself, by their PID (keep the PID from `Start-Process -PassThru` or the launch output; `taskkill /T /PID <pid>` for its own tree). Never stop processes by name, by start time, or by any other filter.

## Architecture

- `lib/vitals.js`: the only place that talks to the SDK (`startSession`, `stopSession`). Native camera capture in the main process (`useCamera`), so the API key never reaches the renderer. Turns each metrics packet into a plain-number payload (`toPayload`: pulse, breathing, hrv, trace). Also `downscaleToRGBA` for the preview. `lib/videofeed.js`: dev-only video input, ffmpeg decodes a file to raw RGB on a pipe and each frame goes to `sendFrame()` (custom input), then is dropped.
- `lib/recording.js`: recorder and replay of the four IPC event channels (`vitals:status`, `vitals:validation`, `vitals:error`, `vitals:metrics`). Recordings are numeric only. `loadRecording` returns `{ events, meta }`. Replay loops at real speed and rebases sample timestamps so the recording's `createdAt` maps to the moment play starts (plus one pass length per loop), which keeps replayed samples on the same clock as `Date.now()`.
- `lib/config.js`: every tunable threshold (calibration, test lengths, late-sample grace, coverage). Retune after the live session.
- `lib/calibration.js`: adaptive calibration, a pure state machine driven with explicit times (see "Calibration" below). `lib/intervals.js`: gap tracker and interval maths. `lib/baseline.js`: median-based calm baseline from the collected samples.
- `lib/questions.js`: loads and validates `questions/*.json` (format in `questions/README.md`); `publicView` strips the answers, which never reach the window.
- `lib/session.js`: one mock-test session (event log, samples, pauses on one clock); `lib/align.js`: question windows, per-question coverage, final answers.
- `lib/report.js`: builds the pressure map from a saved session (pure, `buildReport`). Per question: median and peak pulse change vs the session's baseline, aligned by sample timestamp (a pulse value covers ~12 s and arrives ~8 s late), or "too brief to read" (under `report.minOnScreenSeconds` on screen or under `report.minStablePulseSeconds` measured) or "not measured". Gaps labelled "not measured: <reason>" (validation pauses) and "pulse re-settling" (the no-stable-pulse stretch right after a pause). Each question is analysed over its on-screen windows shifted `report.pulseLagSeconds` (6 s) later, clipped to the test, because a pulse reading trails the body. Rises (>= `riseBpm` for >= `riseMinSeconds`) and recovery, timed from the rise's peak until the first reading back within `recoveredWithinBpm`; hidden recoveries are null, never guessed. Breathing by thirds and HRV by halves only where there are enough readings and a baseline value; otherwise left out entirely. Up to `maxObservations` (3) rule-based observations in this priority order, each only with enough data: biggest rise (a second sentence only if the answer was changed, skipped or marked on that question), settle time after the biggest rise, hard vs easy, breathing last vs first third (only if they differ by >= `minBreathingChangeForObservation`), and last, pulse in the minute before vs after a reset (`resetObsWindowSeconds`, `resetObsMinSamples`), which always adds "This compares two minutes; it can't tell what caused the change." The report carries `pulseLagSeconds`, which the window puts into the "shifted about N seconds later" note. Plus a fixed closing line, `selfReport` ("You said: ..."), `timeline.resets`, and a `summary` for the progress view (score, hard-question median change, settle time after the biggest rise, measured share).
- `report-view.js`: draws the report with plain SVG (no chart library, no network): pulse change timeline with question bands, markers, hatched gaps and labelled reset bands, a breathing chart on the same axis, a question strip, observations. `progress()` draws "Your progress" (one small chart and one plain line per measure, oldest first, no trend labels or direction colours). Okabe-Ito colours, no red/green. Each chart has a screen-reader summary.
- `lib/checkin.js`: the optional "How did that test feel?" answers (Fine, A bit tough, Really overwhelming, Skip), `selfReport`, `saidText`, and `needsSupportScreen` (see the hard rule). `lib/reset.js`: `resetPulseLine`, the one neutral line after a reset outside a test ("Pulse at the start: +14 above your baseline. At the end: +7."), only with `reset.minPulseSamples` stable readings in the `reset.pulseWindowSeconds` before the start and before the end; never says the reset worked.
- 30-second reset (`reset` in config: inhale 4 s, exhale 6 s, 3 cycles): reachable from home, the report, and the test header. A growing and shrinking circle with "Breathe in"/"Breathe out", or a text countdown with `prefers-reduced-motion`. The live breathing waveform is drawn faintly behind it when the camera is on (from home or the report it is off; "Show my breathing" turns it on, with consent, and off again on leaving). No score. With the camera off, the guide waits for "Show my breathing" (then shows "Getting ready" and starts once the breathing trace arrives) or "Start without it", which stays available while waiting. During a test the timer keeps running, the reset shows no numbers, and `reset_start`/`reset_end` are recorded as events (they suspend the current question's window). Main keeps the last 2 minutes of stable pulse for the reset line.
- Check-in and support: after submitting (or time up), the check-in screen comes before the report. The answer goes to main (`test:checkin`), is stored as `selfReport` in the session file (or patched into the file if it was already saved), and the report shows "You said: a bit tough" next to the data, never compared with it. "Really overwhelming" shows a short calm message and the support options, then "Continue to my report" or "Go to home". The support numbers are `tel:` links: the renderer sends them to main (`support:call`), which opens only `^tel:[0-9-]{3,20}$` with `shell.openExternal`. The window never navigates (`will-navigate` is cancelled) and never opens windows. findahelpline.com is plain text; no website ever opens.
- Progress (home, under "Past practice tests"): shown from 3 real sessions (never simulated or dataset ones; dataset sessions are listed apart under "Demo sessions"); before that "Take 3 practice tests to see your patterns." Simulated sessions are never mixed in; in a simulated replay they are shown apart, labelled dev only. Each past session can be deleted on its own (with confirmation, `sessions:delete`, same file-name check).
- `main.js`: window, IPC handlers, live vs replay switch, preview throttling, the 250 ms monitor tick (calm indicator, calibration, test timer), baseline and session storage, delete-all-data. Every SDK event is stamped on arrival with `Date.now()` and passed to the active calibration or test session.
- `preload.js`: exposes `window.vitals` via `contextBridge`.
- `index.html` + `renderer.js`: consent, home (with "Past practice tests" and "Your progress"), calibration, "Before you begin", test (CBT layout), check-in, report, reset, support, settings screens. Past sessions open by file name, checked in main against `^[0-9TZ-]+\.json$` inside `sessions/`. "Save report as PDF" uses `printToPDF` and writes only to the path the student picks in a save dialog. No Node access (`contextIsolation`, `sandbox`). All renderer permission requests are denied. Renderer test events are validated in `lib/session.js` (trust boundary).
- A test starts only once `measureState()` (`lib/calibration.js`, also behind the calm indicator) is `measuring`: position OK and a stable pulse within `pulseFreshSeconds`. Otherwise "Before you begin" shows the reason, retries every second and offers "Start now anyway". Without this, "Start practice test" with a baseline from today turned the camera on cold and Q1 fell in the ~1 minute warm-up (seen in the Step 5 replay).
- The camera session stays on from calibration through the test (restarting would repeat the ~1 minute warm-up) and turns off after the test is saved, or on Back/Stop.
- Preview frames: `videoOutput` (1280x720 RGB) is downscaled in main to ~320 px, throttled to ~10 fps, sent on `vitals:frame` only while the renderer has preview on. Never recorded, logged, or written to disk.
- Storage: `app.getPath('userData')/preppulse-data/baseline.json` (latest calm baseline) and `preppulse-data/sessions/<startedAt>.json` (one file per mock test). Delete all data removes that folder (baseline and sessions) and clears Chromium storage for the app session. Dev recordings live in `data/recordings/` (gitignored, project folder, not user data).
- Session file (`preppulse-session/1`): all times are ms since test start. `events` (test_start, question_shown with `onScreenMs`, answer_selected/changed/cleared, marked_for_review, skipped, navigate, reset_start, reset_end, test_end), `questions` (time, answer, correctness, measured ms, coverage full/partial/none/not_shown, reasons), `coverage` (counts, based on pulse because breathing readings are too sparse to judge one question), `gaps.pauses` (validation/error pauses) and `gaps.noStableReading` (spacing between stable samples above `coverage.*MaxSpacingSeconds`), `samples` (`[t, value, confidence, stable, question]` for pulse, breathing, HRV), `breathingTrace`, `baseline` used, `settings`, `source` (`mode`, `simulated`), optional `selfReport` (`{ feeling, answeredAt }`, the check-in answer). Correctness is computed only at the end, in main.
- Simulated data: `npm run simulate` writes `data/recordings/simulated-test-session.json` (made up, `"simulated": true`, about 13 min: warm-up, calm, three pulse rises with recovery, two `kChestNotVisible` gaps). Replaying it shows a "SIMULATED DATA" banner on every screen, and the session and baseline files carry `simulated: true`; a simulated baseline is ignored outside simulated replay. Never use simulated data in the demo video or the DEV post.
- Input kinds and labels (`lib/source.js`, `describeSource`, pure): the live camera (`dataKind` real, preview on, no banner); a made-up recording (simulated, "SIMULATED DATA" banner); a video file (dataset, banner "Demo input: public research video (UBFC-rPPG, subject 3), not a live webcam" for the UBFC file, "Demo input: test video file, not a live webcam" for any other). The banner is the one fixed `#simBanner` element, so it shows on every screen. A video file never shows frames: main does not subscribe to `videoOutput` (`onFrame` only when `SOURCE.preview`), `vitals:preview` stays off, and the window shows "Preview not available for dataset video". Each kind has its own baseline file (`baseline.json` real, `baseline-dataset.json`, `baseline-simulated.json`) and `readBaseline` ignores a baseline of another kind (`kindOf`). Sessions carry `source.dataset`; home lists them under "Demo sessions", and progress uses real sessions only.
- Decision (2026-11-17, final): the tuning run (Run 1), the network check and the demo takes (Runs 2 and 3) use the live camera, preview hidden. File mode (dataset banner, looping) stays in the code as a tested dev tool only; it is not used for the demo, and a file-mode attempt that day was discarded unanalysed.
- Env (dev/testing only; with none set the app uses the live camera, which the final app uses):
  - `PREPPULSE_REPLAY=<recording.json>`: replays a recording, no camera, no SDK, no credits. Wins over `PREPPULSE_VIDEO`.
  - `PREPPULSE_VIDEO=<file>`: plays a video file instead of the camera: ffmpeg decodes it at its native frame rate (`-re`) and frames go to the SDK's custom input. Any format ffmpeg reads works (the dataset AVIs play as-is, no conversion). Same consent screen, IPC events and recorder. Uses the API key and network like a live session.
  - `PREPPULSE_VIDEO_LOOP=1`: with `PREPPULSE_VIDEO`, plays the file again from the start when it ends (`feedVideo` respawns ffmpeg; frame timestamps keep counting up). Each restart goes through `createRestartGate` (`lib/videofeed.js`): validation reads `kVideoRestarted` ("video restarted") for `video.restartGapSeconds` (12 s), so calibration, the test session and the report record it as a pause ("not measured: video restarted"), and samples timestamped within their signal's analysis window after the restart (`video.restartDropSeconds`: pulse 12, breathing 30, HRV 60 s) are dropped, because they mix the end and the start of the video. The live waveform breaks at any step over 1 s. Diagnostics add `videoRestarts`.
  - `PREPPULSE_FFMPEG=<path to ffmpeg.exe>`: optional; default is `ffmpeg`/`ffprobe` on PATH (installed here via winget, ffmpeg 9.0.1).
  - `PREPPULSE_RECORD=1`: saves live or file sessions to `data/recordings/`.
  - `PREPPULSE_DIAGNOSTICS=1`: on every camera stop, writes `data/diagnostics/<timestamp>.json` (`lib/diagnostics.js`): seconds to first and first-stable pulse, breathing and HRV, pulse spacing, breathing readings per minute, validation and error counts, calibration duration and why it ended, per-question coverage. Numbers and status names only: no frames, hints, answers, values or key.
- `scripts/netwatch.ps1` (`npm run netwatch`): polls the TCP connections of this project's Electron processes every second and writes `data/diagnostics/netwatch-<timestamp>.csv` (remote address, port, reverse DNS, states, first and last seen). Metadata only. Run order for the live session: `docs/live-session.md`.
- Test videos live only in `data/videos/` (gitignored). Never commit them, and never copy or extract frames from them anywhere else.
- Run: `npm install`, copy `.env.example` to `.env`, `npm start`. Probe: `npm run probe` (camera, `PROBE_SECONDS`), `npm run probe -- --video data/videos/<file> [--out <name>]` (file, plays to its end; stops after 60 s of video with no metrics). With `PREPPULSE_DIAGNOSTICS=1` the probe also writes a diagnostics file to `data/diagnostics/`. Video probes mark their recording `dataset` and `notUserData`. Tests: `npm test` (`node --test`: `test/*.js`, synthetic inputs and the simulated recording on a virtual clock).
- Setting the env vars on Windows. In cmd, quote the whole assignment, or the space before `&&` ends up in the path:
  - cmd: `set "PREPPULSE_VIDEO=data\videos\chest-visible.mp4" && npm start`
  - PowerShell: `$env:PREPPULSE_VIDEO = "data\videos\chest-visible.mp4"; npm start` (stays set for the rest of that window; clear with `Remove-Item Env:PREPPULSE_VIDEO`)
  - Git Bash: `PREPPULSE_VIDEO=data/videos/chest-visible.mp4 npm start`
  - The same forms apply to `PREPPULSE_REPLAY`, `PREPPULSE_RECORD`, `PREPPULSE_DIAGNOSTICS` and `PREPPULSE_FFMPEG`.
- `README.md` is for judges and students (setup, replay, troubleshooting, SDK use, consent and data handling). Its "Network connections observed" is a TODO until the netwatch results exist. Line endings are normalised by `.gitattributes` (LF; `.cmd`/`.bat` CRLF).

## Calibration (adaptive, `lib/calibration.js`, thresholds in `lib/config.js`)

- Warm-up: wait until pulse and breathing have each been stable once. Hint "Getting ready, about a minute"; after `warmupHintSlowSeconds` a gentler "still getting ready" hint; after `warmupMaxSeconds` stop without saving.
- Then count calm seconds for pulse and breathing separately: a tick counts for a signal if the position is OK and a stable sample of that signal arrived within its freshness window (`pulseFreshSeconds`, `breathingFreshSeconds`). Done when both reach `minCalmSeconds` and there are at least `minBreathingReadings` stable breathing readings. Sparse breathing extends calibration up to `maxCalibrationSeconds`, then what was measured is saved with an honest note.
- HRV samples count only after `hrvContinuousOkSeconds` of continuous OK position. If none, the baseline stores `hrvRmssdMs: null` ("not enough data yet"); HRV never extends calibration.
- Pauses (non-OK validation, SDK errors) stop counting and are stored in the baseline as gaps with reasons. Only samples collected while measuring go into the medians.
- Status of these thresholds: first guesses. Confirm in the live session (planned around 20 to 21 Nov), which will also be used to record the demo.

## SmartSpectra SDK facts (`@smartspectra/node-sdk` 3.5.0, checked 2026-11-16)

### Packaging and platform

- Pure FFI via koffi, no native build step, no install scripts. Native runtime in per-platform packages (`@smartspectra/node-sdk-win32-x64`, `-darwin-arm64`, `-linux-x64`, `-linux-arm64`); npm installs all four (a few hundred MB), only the matching one loads.
- Requirements: Node >= 20 (24 LTS recommended), Electron >= 28. Linux needs glibc >= 2.35. Windows x64 bundles `opencv_world4100.dll`, `vulkan-1.dll`, `smartspectra.dll`, `smartspectra_capi.dll`, plus tflite face/pose models.
- Packaging: ship `node_modules/@smartspectra/node-sdk-<plat>-<arch>/` as an extra resource (see SDK README).
- If launched from a shell that has `ELECTRON_RUN_AS_NODE` set (VS Code, some Electron-hosted terminals), Electron exits immediately. Unset it.

### Entry points

- `@smartspectra/node-sdk`: `SmartSpectraSDK` (main process), enums, metric bundles, `decodeMetrics`.
- `@smartspectra/node-sdk/main` + `/preload` + `/renderer`: Presage's own Electron bridge where the renderer captures via `getUserMedia` and ships RGBA frames over a MessagePort. Not used here, because its renderer constructor takes the API key in the renderer.
- `@smartspectra/node-sdk/messages`: protobufjs `Metrics` class, `decodeMetrics`.

### Initialisation

```js
new SmartSpectraSDK({
  apiKey,                       // server-validated
  requestedMetrics: [...],      // MetricType ints; default = breathingMetrics
  enableAccumulatedOutput,      // extra 'accumulatedMetrics' packet at session end
  logLevel,                     // SmartSpectraLogLevel.kDebug..kNone, default kWarning
  enableTelemetry: false,       // DEFAULT IS TRUE
});
sdk.useCamera(CameraSelection.default /* | .byId(id) */, { width, height, fps, frameTransform });
sdk.start();                    // throws Error with numeric .code, .message, .retryable
await sdk.stopAsync(); await sdk.destroy();
```

Other inputs: `useCustomInput()` + `sendFrame(buf, w, h, stride, PixelFormat, tsUs)` (monotonic µs timestamps), `useFile(path, opts)`. `SmartSpectraSDK.availableCameras()` lists cameras without a key. On Windows `CameraSelection.front/.back` fail (`kInputUnavailable`); use `default` or `byId`. Only one SDK session per process at a time; await `destroy()` before creating another. `checkDeviceReadiness()` returns `{ verdict: 'ready'|'limited'|'blocked'|'inconclusive', reason }`.

### MetricType codes

- Breathing: `CHEST_BREATHING` 0, `ABDOMEN_BREATHING` 1, `BREATHING_RATE` 2, `BREATHING_RATE_STRICT` 19.
- Cardio: `PULSE_RATE` 15, `ARTERIAL_PRESSURE_TRACE` 16, `HRV` 17, `PULSE_RATE_STRICT` 18.
- Face: `FACE_LANDMARKS` 11, `BLINKING` 12, `TALKING` 13, `EXPRESSIONS` 14.
- Other: `GLUTES_MICROMOTION` 8, `KNEES_MICROMOTION` 9, `EDA_TRACE` 10.
- Unavailable (requesting makes `start()` throw `kConfigurationFailed`): `BREATHING_AMPLITUDE` 3, `APNEA` 4, `RESPIRATORY_LINE_LENGTH` 5, `BASELINE` 6, `INHALE_EXHALE_RATIO` 7.
- Bundles: `breathingMetrics` [0,1,2], `cardioMetrics` [15,16,17], `faceMetrics` [11,12,13,14], `micromotionMetrics` [8,9], `edaMetrics` [10]. A key may not be authorized for every metric (`kMetricNotAuthorized` 13).

### Events (`sdk.on(name, cb)`, one callback per event, later calls replace)

- `processingStatus(status)`: 0 Uninitialized, 1 Idle, 2 Starting, 3 Running, 4 Stopping, 5 Error.
- `validationStatus(code, timestampUs, hint)`: 0 Ok, 1 NoFaceFound, 2 MultipleFacesFound, 3 FaceNotCentered, 4 FaceSizeOutOfRange (deprecated), 5 TooDark, 6 TooBright, 7 ChestNotVisible, 10 CameraTuning, 11 FrameRateTooLow, 12 ExcessiveMotion, 13 FaceTooClose, 14 FaceTooFar, 15 FaceTooHigh, 16 FaceTooLow, 17 FaceNotForward. `hint` is SDK-provided text.
- `metrics(buf, timestampUs)`: protobuf; decode with `decodeMetrics(buf)`. `accumulatedMetrics` same shape.
- `error(code, message, retryable)`: 1 InvalidState, 2 AuthenticationFailed, 3 ConfigurationFailed, 4 CreditExhausted, 5 NetworkError, 6 ServerError, 7 InputUnavailable, 8 ProcessingFailed, 9 FrameConversionFailed, 10 NonMonotonicTimestamp, 11 TimestampGap, 13 MetricNotAuthorized, 14 SustainedLowFrameRate (do not auto-restart).
- Also `frameSentThrough(sent, ts)`, `videoOutput(buf, w, h, stride, fmt, ts)`, `insight(buf, requestId)` (for `requestInsight(text)`, an LLM feature; would send text to Presage; not used).

### Decoded `Metrics` shape (camelCase, protobufjs)

- Sample types: `Measurement { value, stable, timestamp }`, `MeasurementWithConfidence { value, stable, confidence, timestamp }`, `DetectionStatus { detected, stable, timestamp }`, `Strict { value, timestamp, stable }`. Timestamps may be `Long`; `Metrics.toObject(m, { longs: Number })` flattens them.
- `breathing.rate[]` (WithConfidence; `stable` means confidence >= 45, about +/-1 br/min), `breathing.upperTrace[]` (chest waveform), `breathing.lowerTrace[]` (abdomen waveform), `breathing.breathingRateStrict`.
- `cardio.pulseRate[]` (WithConfidence; `stable` means confidence >= 40, about +/-3 bpm), `cardio.arterialPressureTrace[]` (uncalibrated, unitless), `cardio.hrv[] { rmssd, meanNn, sdnn, baevsky, confidence, stable, timestamp }` (`stable` at confidence >= 50), `cardio.pulseRateStrict`.
- `face.blinking[]`, `face.talking[]` (DetectionStatus), `face.landmarks[] { value: [{x,y}], stable, reset, timestamp }`, `face.expression[] { scores: [{ type, confidence 0..100 }] }`; ExpressionType: ANGRY, CONTEMPT, DISGUST, FEAR, HAPPY, NEUTRAL, SAD, SURPRISE. Expression labels carry emotional connotations; do not present them as feelings or states of mind.
- `eda.trace[]`, `micromotion.glutes[]`, `micromotion.knees[]`.
- Also a deprecated-looking `pulse { rate, trace, pulseRespirationQuotient }` message exists in the proto; the docs use `cardio.*`.
- Latest value idiom: `m.cardio?.pulseRate?.at(-1)?.value`.

### Confirmed by live probe (`npm run probe`, Windows 11, Integrated Camera, 2026-11-16)

- **Pulse needs `ARTERIAL_PRESSURE_TRACE` (16).** With [0,2,15,17] no `cardio` data arrived at all in 45 s and no error was raised. With [0,2,15,16,17] pulse appeared. The app requests [0,2,15,16,17] (`lib/vitals.js`).
- **Timestamps are microseconds since the Unix epoch** (event `timestampUs` and every sample `timestamp`, same clock; matches `Date.now() * 1000` within ~30 ms).
- **Arrays are incremental.** Each packet carries only new samples (0% repeated timestamps across 1000+ packets). A packet only contains the groups with new data (often just `breathing` or just `cardio`).
- Packet cadence follows frames: median gap 33 ms, about 15 to 26 packets/s, irregular (p95 60 to 110 ms; one 6 s stall with the arterial pressure model on). The breathing trace (`upperTrace`) has about one sample per frame (~32 ms spacing).
- Start to `kRunning` takes ~5 s (includes the key check). First packet ~0.1 s after `kRunning`.
- **Warm-up is long.** Pulse: first sample 45 s after `start()`, about 27 s after the face became continuously OK, and samples arrive ~8 s after their own timestamp. Confidence 0.5 to 26, never `stable` within 45 s. Breathing rate: sparse (1 to 9 samples per 45 s), first `stable` at 46 s (value 3.5, confidence 79, which looks implausibly low). HRV: never appeared in 45 s. Plan calibration UX for several minutes, not seconds.
- Validation fires once per frame (~30/s). Hints seen: kOk "Hold still and record.", kNoFaceFound "No face found.", kTooDark "Increase light on face.", kChestNotVisible "Place more of the chest in view.", kFaceNotForward "Face the camera.", kMultipleFacesFound "Only one face is allowed."
- **The SDK will not start measuring until the face and upper chest are in view.** A 180 s probe with the student too close (5296 of ~5350 frames `kChestNotVisible`) stayed in `kStarting` the whole time and produced zero metrics packets, with no error. Show the validation hint before any "starting" message, and tell students to sit back so the upper chest is visible.
- Status names arrive as `kIdle`, `kStarting`, `kRunning`, `kStopping` (the enum key names).
- `videoOutput` IS delivered with `useCamera`: 1280x720, `PixelFormat.kRGB` (0), stride 3840, ~29.5 fps.
- Still unknown: how long pulse and HRV take to reach `stable`, and whether a bad-face period resets the warm-up.

### Video file input (`useFile`) and capture guidance (Presage docs, 2026-11-16)

- `useFile(path, { timestampsPath, interframeDelayMs, startOffsetMs, maxDurationMs, frameTransform })`. The file "plays through the same pipeline as a live camera"; end of file shows as a transition to `kIdle`.
- Formats: docs only say "Use a widely-supported container/codec such as MP4 (H.264)". macOS/Linux bundle FFmpeg 6.1.1 (LGPL build).
- **`useFile()` cannot open normal video files on Windows in SDK 3.5.0** (confirmed 2026-11-16 with `OPENCV_VIDEOIO_DEBUG=1`). The bundled `opencv_world4100.dll` has every real decoder (MSMF, FFMPEG, GSTREAMER, INTEL_MFX) as a plugin DLL (`opencv_videoio_<name>4100_64.dll`), and none ship in `@smartspectra/node-sdk-win32-x64`. Only the built-in CV_IMAGES and CV_MJPEG readers exist. Both an MPEG-4 Part 2 AVI and an H.264 MP4 failed with "Video file source cannot start: Failed to open video file" then `kInputUnavailable`. The live camera is unaffected (different capture path). Worth reporting to Presage.
- Chosen workaround (working, 2026-11-16): `lib/videofeed.js` decodes with ffmpeg into a pipe and pushes raw RGB frames through `useCustomInput()` + `sendFrame()` with epoch-µs timestamps spaced by the file's frame rate. Frames stay in memory, no OpenCV involved. On end of file it calls `stopAsync()`, so status goes kStopping then kIdle like `useFile`. Verified: 5355 frames at 30 fps accepted, `videoOutput` delivered (640x480 kRGB). Not tried: MJPEG AVI for the built-in reader, or adding OpenCV's FFmpeg plugin DLL.
- **With custom input, `kRunning` arrives ~0.2 s after `kStarting` even while a positioning hint blocks measurement** (with the camera it stays `kStarting`). Never treat `kRunning` as "measuring": use `validationStatus` kOk plus actual stable samples.
- **The chest check applies whatever metrics are requested.** Requesting only [15,16,17] (no breathing) still gave `kChestNotVisible` on every frame and zero metrics.
- Files below 25 fps (half of the dataset is 24 fps) are under the SDK's sustained frame-rate floor; use 30 fps files.
- Frame rate: the SDK measures it from timestamps (the optional timestamps file, one per line, else the video's playback position), not from `interframeDelayMs`. Capture at 30 fps; sustained >= 25 fps is required (`kSustainedLowFrameRate`, not retryable for files). No resolution is specified; the live camera runs at 1280x720, so record 720p.
- Network and key: file sessions authenticate against Presage's service ("No offline mode"). Docs do not say whether file sessions consume credits differently; assume they cost the same as camera sessions. Credits are counted per account. Use replay (`PREPPULSE_REPLAY`) to iterate for free.
- Analysis windows (minimum data before a value can be trusted): pulse rate 12 s, breathing rate and waveforms 30 s, HRV 60 s. Confidence starts at 0. Don't surface a value before its window has elapsed and `stable` is true.
- Capture conditions: one face, centred, facing the camera, even diffuse light, no backlight or flicker; upper chest visible and unobstructed; stationary camera; sit still, no talking, no chewing gum; plain light-coloured clothing (avoid dark or high-contrast stripes); wait for `kCameraTuning` to clear.

### Decision: no facial expression metrics

Never request `EXPRESSIONS` (14) anywhere in the app, nor `FACE_LANDMARKS` (11). Emotion labels such as FEAR or ANGRY are judgements about the student, which conflicts with the no-diagnosis rule. Landmarks are face geometry we have no use for.

### Network and telemetry

- `apiKey` is validated against Presage's server, so a network connection is needed to start a session (errors `kNetworkError`, `kServerError`, `kCreditExhausted` exist). Per-use credits appear to be metered server-side.
- At start the SDK also downloads encrypted model files from Presage (log: `secure_model_loader ... Failed to fetch encrypted blob for model_id=phasic-bp-inference` when a start was cancelled; that is the arterial pressure model, needed for pulse). The device-key cache lives under `%LOCALAPPDATA%\SmartSpectraSDK` (plain Node) or the Electron cache folder.
- Telemetry defaults ON. When on, Presage receives: session summaries (SDK build, platform/OS/device model/CPU arch, input source kind and outcome, count of requested metrics, throughput/timing stats, validation-state counts, coarse error code, timestamp) and full device-readiness reports (device/OS, requested metrics, camera settings, performance checks, free-text diagnostics). Sent over the SDK's authenticated, TLS-pinned channel and linkable to the account/device. Presage says it never includes video frames or measured vitals.
- `enableTelemetry: false`: per Presage docs "the SDK starts no telemetry session and transmits nothing" for telemetry. Auth traffic still happens. No retention limit is configured for reports on Presage's side.
- Not yet verified with a network capture. Verify before writing the privacy section of the submission.
